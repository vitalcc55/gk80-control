# Первый сквозной демонстрационный проход

Статус: **активный план**. Исходная точка — `81565e795848b48bb82c624bdaeca0553ef1b96d`. Этот план фиксирует ближайший результат задач [#3](https://github.com/vitalcc55/gk80-control/issues/3), [#4](https://github.com/vitalcc55/gk80-control/issues/4), необходимой части экранов [#6](https://github.com/vitalcc55/gk80-control/issues/6), минимального уровня A [#8](https://github.com/vitalcc55/gk80-control/issues/8) и применимых проверок [#10](https://github.com/vitalcc55/gk80-control/issues/10). Полное закрытие этих задач и последующая работа по #5–#7 не подразумеваются.

## Результат и границы

Из согласованных экранов оператор создаёт демонстрационное испытание ручного клапана на нагнетание. Отдельное Go-ядро принимает команды, управляет симулятором, возвращает изменяющиеся измерения, выполняет упрощённое завершение и отдельную процедуру остановки и сохраняет запись в SQLite. После перезапуска запись открывается из истории. Тот же путь затем проверяется через один локальный IAB-вход с тем же настроенным demo-профилем. Макет `ui:fixtures` остаётся автономным и явно помеченным; работающие с core экраны постоянно обозначаются «Демонстрация · тестовые данные».

Это первый упрощённый проход, а не реализация полной методики одной точки. Реальные драйверы, стенд, разрежение, привод, полноценные роли, официальный протокол, расчёт расхода и класса, полный алгоритм и все отказы последующей демонстрации не входят в результат. Копирование, импорт и объединение баз, управление несколькими профилями, универсальный перенос браузерного состояния и полноценное автосохранение черновиков также вне этого этапа. Временные правила и неблокирующая граница оборудования относятся к demo и не утверждают состояние или поведение реального стенда.

## Инварианты

- Core независимо собирается и владеет состоянием, командами, симулятором, аудитом и SQLite; Wails — тонкий адаптер, React — отображение и несохранённый ввод. Источник контракта — OpenAPI и схемы событий, с генерацией Go DTO и привязок Wails.
- Core слушает только `127.0.0.1`; HTTP и WebSocket защищены случайным межпроцессным секретом, не попадающим в URL, аргументы, логи или frontend. Для профиля допускаются одно ядро, одно активное испытание и один активный UI-клиент; второй получает отказ.
- Повтор `commandId` не повторяет действие, а повтор с другим содержимым отклоняется. Принятие, выполнение и сохранение различаются. При неизвестном результате или пропуске событий интерфейс получает снимок, не повторяя команду автоматически. Версия API, `backendRunId`, ревизия, последовательность событий и граница снимка позволяют обнаружить перезапуск и пропуски; при разрыве потока показания становятся неактуальными или неизвестными до восстановления.
- Параметры, оператор demo, измерения с единицами, временем, качеством и источником, команды и аудит сохраняются ядром. Изменение состояния и соответствующее событие атомарны. После аварии испытание не возобновляется автоматически. При отказе обязательной записи новые старты и обычные изменяющие действия отклоняются до выполнения; остановка остаётся доступной, её исход и сохранение показываются раздельно.
- Отсутствующее измерение не равно нулю; запрос остановки не доказывает её выполнения или безопасного давления. Расход не рассчитан, класс не определён. История читается из core, а не воссоздаётся из подготовленных примеров.
- Browser-host допускает только demo и автоматически подключает локальный IAB без браузерной авторизации по решению пользователя от 3 ноября 2026. Проверки Host/Origin и номер соединения не являются авторизацией: другие локальные процессы могут обращаться к режиму. При разрыве связанные запросы отменяются; после refresh снимок восстанавливается без повтора команды. IAB и desktop последовательно используют одну историю. Закрытие вкладки не подтверждает остановку; после ограниченного времени восстановления клиента core применяет документированную demo-процедуру прерывания.
- Общий ограниченный `slog` с отдельными JSONL для core и desktop обнаруживает ошибки writer, не блокирует управление и не записывает секреты или полные полезные нагрузки. Предметный аудит остаётся в SQLite.

## Проверка и условия остановки

Проверки этапов должны доказывать конкретный контракт: генерацию и совместимость типов, отдельный процесс, защиту HTTP/WS, повторы и коллизии команд, события и восстановление снимка, атомарность записи и повторное чтение, отказ хранения и доступность остановки. UI-проверка показывает ожидание и подтверждённое состояние; сборка, fixture и настоящий обмен подтверждают разные свойства. Для frontend действуют `check:quick` во время правок и `check:pr` перед передачей; проверки Go и интеграции добавляются по мере появления кода.

Работа останавливается для решения пользователя только при неразрешимом существенном продуктовом или договорном противоречии, требовании отдельного внешнего разрешения, невозможности безопасно обеспечить обязательный инвариант или доказанном внешнем блокере. Открытые вопросы настоящего стенда не блокируют явно ограниченный demo. Полная приёмка #7, включая привод, потерю ДД1 и остальные сценарии, остаётся отдельной работой.
