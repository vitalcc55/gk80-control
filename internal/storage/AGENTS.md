# Сохранённые факты и транзакции

## Ответственность Store

SQLite открывает и изменяет core. `Store` владеет сохранёнными записями, идентичностью команд, ревизией и авторитетным аудитом. Он не управляет оборудованием, lease, UI или временем этапов.

Engine определяет оперативный переход; Store проверяет предусловия и сохраняет результат атомарно. SQL guards защищают состояние внутри транзакции: не удаляйте их как дублирование Engine и не создавайте здесь второй алгоритм испытания.

## Контракт записи и чтения

- Записывайте соответствующие состояние, команду и аудит одной транзакцией. Ошибка обязательной записи не оставляет частичный успешный переход.
- Возвращайте фактический [результат commit](../../docs/engineering/store-results.md). Подготовленные значения не подтверждены; нулевая ревизия допустима и не обозначает отсутствие данных.
- Различайте новый переход, replay/no-op, сохранённый отказ и неизвестность. `err == nil` не обязательно означает новый переход; ошибка ответа не доказывает отсутствие commit. Отмена запроса не отменяет уже известный commit.
- Тот же command ID и содержимое не повторяют действие/аудит; другое содержимое даёт конфликт. Exact lookup выполняет чтение. Исторический результат не становится текущим snapshot.
- Страницы истории, измерений и аудита имеют определённый порядок и ограниченный размер. Поиск всей истории выполняется над всей подходящей выборкой Store/core, не над загруженной страницей UI.

## Данные и схема

База находится в выбранном пользовательском профиле отдельно от установки. Путь принадлежит core: последовательные desktop/IAB-запуски одного demo-профиля читают ту же историю. Refresh и новая версия сами по себе её не очищают; параллельные проверки используют отдельные временные профили.

Сохраняйте канал, единицы, время, источник, качество, demo-признак и идентичность испытания. Отделяйте исход, полноту данных и сохранение. Восстановление фиксирует неполный/прерванный проход без возобновления оборудования.

Перед изменением схемы определите данные, которые нужно сохранить. Не поддерживайте неиспользуемые форматы и универсальные миграционные слои; после перехода потребителей удаляйте ненужную ветку. История пользователя и неразрешённые команды не являются одноразовыми fixtures: их потеря/reset требуют явного решения, не скрытого эффекта запуска версии.

Используйте текущий путь Store. Второе соединение UI или обход транзакционных методов ради экрана нарушают владение. Отказ JSONL writer отличается от ошибки SQLite; технический лог не заменяет аудит.

## Проверка изменений

Изменённую транзакцию проверяйте на временной SQLite: commit/reopen, rollback при отказе обязательной записи, точный повтор и конфликт. При изменении семантики отмены/неизвестного commit проверяйте её отдельно. Для чтения проверяйте страницы, фильтрацию всей выборки и изоляцию баз; для схемы — реально поддерживаемый путь сохранения данных.

## Code Review Rules

- Отмечайте подтверждение до commit, частичное сохранение и неатомарный аудит.
- Отмечайте lookup с побочным действием, утрату идентичности и replay со старым этапом как текущим.
- Отмечайте скрытое удаление истории/неизвестных команд, второй writer и оборудование внутри транзакции.
