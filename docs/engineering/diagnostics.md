# Диагностика процессов

В `internal/diagnostics` подготовлена общая основа `slog`/JSONL для desktop и core. Это ещё не подтверждение уровня A: файлы реальных процессов, сквозной обмен и поведение при недоступном core проверяются после подключения обеих точек входа. Аудит испытаний и измерения принадлежат SQLite, не этому журналу.

Каждый запуск получает собственный файл `<role>-<process_run_id>.jsonl` в каталоге логов demo-профиля вне установки и исходников, например `%LOCALAPPDATA%\GK80\demo-gk80-control\logs`. Примерный каталог и профиль для рабочего ПК описаны в [окружении](development-environment.md); параллельные копии используют разные профили. Идентификатор запуска core совпадает с `backendRunId`, при необходимости host также записывает этот идентификатор для корреляции.

В записи есть версия схемы, время UTC, уровень, фиксированное сообщение, код события, компонент, роль и идентификатор запуска процесса, PID, версия сборки, профиль и режим; при наличии добавляются существующие `command_id`, `test_id`, `action_id`, `backend_run_id`, разрешённый код причины и код выхода. Прикладные компоненты используют `Application` и обычный `*slog.Logger`: сообщением служит код события из каталога, а `With` передаёт только разрешённые идентификаторы и значения. Идентификаторы принимаются как UUID или его строка; группы не поддерживаются. Неизвестные сообщения и сгруппированные записи отбрасываются с учётом потерь, произвольные атрибуты не записываются. Каталог ограничен событиями старта/выхода процесса, ошибки соединения и принятия/отклонения/выполнения команды. Его расширяют при появлении реального поведения, а не произвольным текстом или телом запроса. Адаптеры Wails и библиотек заменяют сообщения и атрибуты фиксированными `framework.message` и `library.message` с соответствующими компонентами, framework DEBUG отключён. Секреты, payload и произвольные ошибки не передаются в журнал.

Очередь ограничена, отправка записи не ждёт файлового I/O. Один worker владеет файлом; текущий файл ограничен 16 МиБ, а короткая запись, ошибка writer, переполнение очереди и достижение лимита переводят статус в degraded и учитывают потерянные записи по уровням. Частичная запись может оставить неполный последний фрагмент JSONL; предыдущие полные строки остаются читаемыми, а дефект отражается в статусе. Fallback пробует один фиксированный текст через отдельный worker, не через тот же logger и не через stdout core; его успех при зависшем или неисправном выводе не гарантирован. Закрытие ожидает освобождения writer и попытки fallback не более двух секунд или до более раннего переданного deadline. После аварийного завершения сохранность очереди не обещается.

Полная ротация, очистка и общий бюджет закрытых файлов разных запусков относятся к уровню Б #8; текущий модуль не ограничивает их суммарное накопление. Его файловая диагностика не останавливает испытание и не подтверждает сохранение аудита. Состояние writer и потерь доступно через `Status`; подключение этого состояния к интерфейсу и диагностика React остаются последующими этапами.

Локальные целевые проверки: после подключения окружения выполнить `go test ./internal/diagnostics` и `golangci-lint run ./internal/diagnostics/...`. Тесты используют временные каталоги и управляемые ошибки/блокировки writer. `go test -race -count=1 ./internal/diagnostics` выполнен в Ubuntu/WSL с Go 1.27.3 и GCC 13.3; это проверка конкурентного модуля в Linux, не проверка Windows-процессов или файловых особенностей. Windows race-профиль с C-компилятором ещё не подготовлен.
