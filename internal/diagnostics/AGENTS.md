# Диагностика процессов

## Назначение и владение

`Logger` владеет одним writer и ограниченной очередью процесса. Производные handlers используют их без новых worker/callbacks. JSONL объясняет наблюдения; авторитетные состояние и аудит принадлежат core/SQLite. Новая диагностика отвечает на конкретный вопрос, не создаёт вторую систему допуска команд.

## Допустимые сведения

- Добавляйте события, категории и операции через явный каталог. Известная точка наблюдения не доказывает первопричину: ошибка `app.Run` сама по себе не означает отказ WebView2.
- Записывайте только разрешённые ограниченные поля. Не сериализуйте произвольные сообщения Wails/библиотек, attrs, `error`, `LogValuer`, payload, массивы измерений, секреты и пользовательские формы ради одной диагностической задачи.
- Берите корреляционные ID из контекста операции. Текущий Owner при обработке поздней ошибки не доказывает её связь с текущими backend/test/command. Неподтверждённый ID оставляйте отсутствующим.
- Сохраняйте источник и смысл уровня. Отказ технической записи не подтверждает остановку, сохранение или неуспех испытания.

## Ресурсы и отказ

Постановка записи не ждёт файлового I/O. Переполнение, короткая запись и отказ writer дают наблюдаемый degraded-статус и корректный учёт потерь. Fallback не использует сломанный logger и не мешает служебному обмену core.

При ротации определите владельца активного файла, бюджет файлов разных запусков, очистку и поведение при её отказе. Не удаляйте чужие/используемые файлы; используйте существующий writer.

Закрытие ограничено сроком и сообщает неподтверждённое завершение отдельно. Сохранность очереди после аварии не гарантируется. Отказ/зависание writer не блокирует управление и остановку; host диагностирует собственные отказы при недоступном core. Изменение hooks не должно скрыто менять фатальность или shutdown приложения.

## Проверка изменений

Для полей/lifecycle используйте [описание диагностики](../../docs/engineering/diagnostics.md). Проверяйте конечный JSONL, каталог code/operation, отсутствие raw-данных и секретов. Очереди, ротацию и shutdown проверяйте временными файлами и управляемыми отказами/блокировками writer, включая штатный путь. Race применяйте при изменении конкуренции. Изменённые Windows/Wails hooks проверяйте на настоящем фреймворке; unit-тест mapper не подтверждает вызов callback фреймворком.

## Code Review Rules

- Отмечайте произвольные тексты/атрибуты, выдуманную корреляцию и точку наблюдения, представленную как причина.
- Отмечайте неограниченный рост, рекурсивный fallback, I/O на пути управления и несколько writer ресурса.
- Отмечайте зависимость допуска/успеха команды от технического logger. Обязательный предметный аудит записывает Store.
