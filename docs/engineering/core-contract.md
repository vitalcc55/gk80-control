# Контракт первого demo core

Статус: реализуется первый упрощённый проход. Окно Wails запускает отдельно собираемый core и подключает согласованные экраны к его предметным операциям. Core запускает SQLite и demo-движок, предоставляет право UI, снимок, поток событий, создание, готовность, запуск, подтверждение, остановку, чтение статуса команды и истории. Оставшиеся проверки desktop и локального IAB перечислены в [плане](first-core-demo-plan.md). [OpenAPI](../../api/core.yaml) — единый источник HTTP-моделей и полезных нагрузок событий. Перечисленные операции не считаются реализованными только потому, что они описаны в схеме. Параметры, состояние, история и измерения принадлежат ядру; модели `src/model.ts` относятся к подготовленному макету.

## Процессы и доступ

Desktop запускает отдельный core с demo-профилем. Core удерживает блокировку профиля до выхода; два ядра и два активных UI-клиента для одного профиля не допускаются. Путь SQLite определяется профилем и располагается в пользовательском каталоге постоянных данных, отдельно от установки. Процессы тестов получают отдельные временные профили.

В дополнение к межпроцессному секрету core выдаёт одному UI-клиенту право управления (`ui-lease`) сроком 30 секунд; его можно явно продлить или освободить. Второй клиент получает отказ; восстановление требует идентификатор клиента и ранее выданное право. Host продлевает право только по подтверждению активности React. При неизвестном исходе получения нового права host не отправляет повторный запрос в этой сессии. WebSocket core закрывается при отзыве или истечении права. Локальный IAB работает без отдельной браузерной авторизации; номер соединения связывает запросы с его жизненным циклом, но не удостоверяет клиента.

Получение права и его первый срок допускаются движком атомарно; получение и продление проверяют отмену запроса после ожидания блокировок до изменения состояния. Отмена до допуска не создаёт право и не меняет его срок, не отзывает существующего владельца и не запускает остановку. После допуска действие может завершиться, даже если клиент потерял ответ; такой результат остаётся неизвестным до подтверждения. Ожидание блокировок само по себе не прерывается отменой контекста и не является доказательством немедленного завершения запроса.

Core допускает одновременно не более одного изменения права UI; остальные получают `409 lease_operation_in_progress`, не означающий занятого права. Чтение тела POST ограничено отдельно и не задерживает продление или освобождение права; сетевой ответ не удерживает допуск изменения. Этот отказ подтверждает только недопуск нового запроса, а не исход предыдущего. Освобождение также проверяет отмену до допуска; после допуска отзыв не откатывается. Ограничитель не используется командами испытания и сам по себе не устраняет ожидание Stop на общих блокировках движка и права. Запросы, задержанные до входа в обработчик, и последствия уже допущенного действия могут оставаться неопределёнными.

Для первого handshake host создаёт случайный секрет и передаёт его дочернему core по закрытому каналу стандартного ввода, не через аргументы или переменные окружения. Core после блокировки профиля открывает только `127.0.0.1` на свободном порту и сообщает адрес, версию, demo-признак и идентичность через канал стандартного вывода. Клиент проверяет отпечаток временного TLS-сертификата до отправки bearer, не использует proxy и не следует перенаправлениям. На Windows процессный тест проверяет защиту bind от повторного захвата адреса. WebSocket использует тот же защищённый клиент и подключён к владельцу сеанса в host.

При неверной или отсутствующей авторизации handshake отвечает фиксированным JSON `ApiError` и `WWW-Authenticate: Bearer`, не повторяя переданный токен. На Windows desktop запускает консольный core без отдельного окна и сохраняет его стандартные каналы.

Host управляет только запущенным им процессом и ожидает его завершения. При появлении активного испытания закрытие канала владельца и исчезновение UI должны обрабатываться документированной demo-процедурой с ограниченным временем восстановления; ни исчезновение вкладки, ни запрос остановки не подтверждают безопасного давления. Browser-host используется только для локальной демонстрации и не входит в desktop-поставку.

Пока испытание не запущено, закрытие канала владельца завершает пассивный core; если завершение не подтверждено, host сохраняет ссылку на собственный процесс для очистки в течение своей жизни; при выходе сообщает о неподтверждённом результате. Обычное завершение host ждёт до шести секунд с учётом последовательных ограничений сервера и диагностического writer. Необработанные stderr-данные core не записываются: известный фиксированный fallback преобразуется в сигнал об отказе диагностики. При занятом профиле окно показывает отдельную причину; host записывает события соединения и завершения в отдельный журнал.

## Команды и сохранение

Последний принятый пакет в оперативном снимке имеет `measurementBatch`: до него поле равно `null` и массив измерений пуст; после него номер начинается с единицы и увеличивается на один с каждым принятым пакетом этого испытания. Номер и показания публикуются вместе и остаются доступными при остановке и завершении. Пропуск между полученными номерами означает неполученный UI пакет, но не доказывает потерю записи Store. Пропущенные значения не восстанавливаются этим полем.

Первый внутренний demo-движок моделирует ручной клапан на нагнетание: после подтверждения оператора он выдаёт синтетические отсчёты ДД1, ДД2 и ДД3, удерживая давление около Pmax. Это демонстрационная функция, а не модель стенда. Длительность отсчитывается монотонно от первого отсчёта и округляется вверх до наносекунды. Остановка порта не ждёт SQLite; принятые в ограниченную очередь измерения записываются до фиксации прерывания, а потеря пакета отражается в качестве, сохранении и аудите. При задержке записи результат сохранения остаётся неизвестным до подтверждения; `Refresh` разрешает известную в памяти финализацию чтением и записью без повторного действия симулятора. Этот внутренний механизм ещё не проверяет сетевое восстановление или жизненный цикл приложения.

Временное правило demo: если отдельная запись измерений не возвращается в течение двух секунд, ядро инициирует системное прерывание с причиной `measurement_write_timeout` и останавливает симулятор независимо от SQLite. Тайм-аут сам по себе не означает потерю измерений или завершённый откат: запись не повторяется, принятая очередь ожидает исхода, а сохранение остаётся неподтверждённым до фиксации и повторного чтения результата. Это правило не является требованием к реальному стенду.

Если подтверждение запуска уже поступило, но обязательная запись завершения запуска не возвращается в течение двух секунд, core инициирует системную остановку с причиной `storage_error`, не ожидая возврата этой записи. Пока её исход неизвестен, очередь изменяющих команд и завершение ядра остаются неподтверждёнными. Это ограничение относится к демонстрационному движку и не подтверждает состояние реального оборудования.

Создание через HTTP проверяет исходный JSON до преобразования в DTO и сохраняет точную идентичность чисел. Исторический отказ или конфликт ищется до допуска нового действия; потерянный ответ разрешается чтением команды и снимка. `404` означает отсутствие известной записи на момент чтения и не доказывает, что параллельная команда не будет выполнена. Пока исход создания не определён, статус может быть `unknown`, а снимок временно недоступен. Известную остановку с неподтверждённым сохранением снимок продолжает показывать. Отменённое чтение SQLite, которое не возвращается, удерживает очередь изменяющих команд до фактического завершения; это не блокирует независимую остановку.

Внутреннее чтение SQLite выдаёт ограниченные страницы списка испытаний в устойчивом порядке UUID, а не в хронологическом порядке. Отдельные страницы не образуют общий снимок: новые записи до текущего курсора видны при следующем обходе. Для измерений и аудита курсор основан на фактической последовательности, а конец определяется дополнительной строкой. Наличие сетевого маршрута и его параметры этот внутренний интерфейс пока не подтверждают.

Все предметные изменяющие команды имеют `commandId`. Core сначала распознаёт повтор по ID и содержимому, затем проверяет ревизию и допустимость нового действия. Повтор не выполняет действие второй раз, тот же ID с иным содержимым отклоняется. `202` означает принятие, а не выполнение; повтор уже обработанной команды возвращает её известное состояние, включая ошибку выполнения. При неизвестном ответе host запрашивает состояние или команду, не отправляя её автоматически повторно. Подтверждения оператора относятся к новому испытанию и проверяются ядром при старте.

Если сохранённая остановка отменяет ещё ожидающее подтверждения действие запуска, команда запуска получает конечный статус `failed` с причиной `canceled_by_stop` в той же транзакции и аудите. Если подтверждение уже записано и выполнение запуска могло начаться, незавершённая команда остаётся `unknown`: сама остановка не доказывает исход запуска. Ранее сохранённые неизвестные команды этим правилом не переписываются.

Входная граница HTTP проверяет структуру исходного JSON по встроенному OpenAPI до декодирования в DTO и сохраняет точное десятичное содержимое команды создания для сравнения повторов. Эквивалентные числовые записи совпадают; разные значения не сливаются при округлении в `float64`. Существующие записи не переписываются, и точность, утраченную до их сохранения, восстановить нельзя. Структурно корректный ранее сохранённый отказ допускается искать до полной проверки новой команды; эти свойства проверены через отдельный процесс.

Нативный Go-клиент предоставляет только предметные HTTP-операции и проверяет полученный JSON по OpenAPI до декодирования; ответы ограничены четырьмя МиБ. `202` сохраняется как `accepted`, а `rejected` и `failed` в подтверждённом ответе остаются статусами команды. При потере или повреждении ответа изменяющей операции и при отказе права после отправки её исход считается неизвестным; повтор автоматически не отправляется. Владелец demo-сессии управляет правом и потоком; предметные вызовы зарегистрированы в Wails, а состояние доставляется общим экранам desktop и IAB. Область фактических проверок приведена в [журнале](first-core-demo-verification.md).

Граница команд Wails проверяет полученный JSON до декодирования и сохраняет его для core. Для нового создания число, изменившее значение при преобразовании в `float64`, отклоняется после чтения статуса команды; известный повтор передаётся ядру для проверки его исходной идентичности. Журнал desktop фиксирует идентификаторы команды и запуска и безопасные причины неизвестного исхода без тела запроса.

Параметры клиента представлены `float64`: исходный десятичный текст к этой границе уже может быть округлён. Подключённая форма проверяет сохранение десятичного значения при преобразовании и отклоняет ввод, который не сохраняется. Проверка исходного JSON и `CreateExact` в core продолжают действовать для фактически отправленных чисел.

При создании испытания core заранее выделяет и вместе с записью сохраняет `stopCommandId`, предназначенный только для остановки этого испытания. Остановка имеет фиксированное содержимое и доступна при устаревшей ревизии или отказе записи; в работающем процессе её повтор не инициирует процедуру заново. Если записать результат невозможно, состояние сохранения остаётся ошибочным или неизвестным. После аварии испытание не возобновляется, а повтор зарезервированной остановки не возобновляет процедуру. Этот вариант требует проверок отказа SQLite, повторов, коллизий и аварийных окон до заявления о выполнении инвариантов.

Изменение сохраняемого состояния и соответствующий аудит записываются одной транзакцией. При отказе обязательной записи новые старты и обычные изменяющие действия не выполняются; остановка не зависит от успешной записи. Аудит не подменяется JSONL-диагностикой. Исход, качество данных и сохранение различаются; отсутствие значения не является нулём. До согласования расход не рассчитывается, класс не определяется.

Основа хранения использует SQLite без CGO (`modernc.org/sqlite`): при старте core открывает `demo.sqlite` только после блокировки профиля и отказывает при неизвестной версии схемы. Создание сохраняет параметры, оператора, идентификатор остановки, команду и аудит одной транзакцией; повтор распознаётся до проверки ревизии. После ошибки обязательной записи экземпляр хранилища не принимает новые изменения. Операции доступны через API; поведение остановки при отказе хранения проверено на уровне движка и жизненного цикла core.

База проверяет фактические `journal_mode=WAL`, `synchronous=FULL` и включённые внешние ключи; версия SQLite и настройки записываются в диагностический журнал core. Схема версии 2 сохраняет инструкции действий и пакеты исходных отсчётов, сохраняя историю версии 1. Пакет ограничен 128 отсчётами; граница потерянного при аварии неподтверждённого хвоста и очередь определяются при подключении движка. Для новых испытаний demo-интервал измерения ограничен 3600 секундами, старые параметры читаются без изменения. Внутренний критерий полноты требует не менее двух достоверных отсчётов ДД1, покрывающих заданный интервал по монотонному времени двигателя, без недостоверных отсчётов ДД1; абсолютные метки сохраняются для истории. Это не утверждённая методика реального стенда.

## Поток и восстановление

Клиент подписывается на авторизованный WebSocket и после `StreamReady` буферизует события. Затем получает согласованный `Snapshot` с `backendRunId`, ревизией и `lastEventSequence`, отбрасывает события до границы снимка и применяет следующие по порядку. При смене запуска, пропуске, переполнении или разрыве поток восстанавливается новым снимком; до восстановления прежние показания не считаются актуальными. Host сообщает интерфейсу состояние соединения отдельным типизированным событием `core:connection` и предоставляет его начальное значение. UI подписывается до чтения начального состояния и применяет только более новую ревизию данного `hostRunId`; смена host означает новое восстановление. `live` разрешён лишь после согласованного снимка и потока. Очереди ограничены, потеря событий не скрывается. Времена наблюдений абсолютные, время последнего достоверного измерения указывается отдельно; таймеры принадлежат ядру. Чтение исходных отсчётов и аудита ограничено страницами: последовательности начинаются с 1, курсор 0 или его отсутствие означает начало. Пустые обязательные коллекции кодируются массивом `[]`, а не `null`.

Wails предоставляет единое `SessionView`: состояние связи, последнюю копию снимка и `validForMs`, верхнюю границу срока актуальности снимка. Отдельные `linkValid` и `linkValidForMs` показывают подтверждение канала, права и heartbeat независимо от текущего обновления снимка. Они не разрешают команды и не делают показания актуальными. Клиент отсчитывает оба срока от монотонного начала запроса, включая задержку ответа; ноль означает немедленное истечение. Изменение состояния, ошибка или разрыв могут отменить подтверждение раньше. Снимок при `recovering` или `disconnected` остаётся только последним известным; ревизия host учитывает обновления измерений при равной ревизии core, а поколение потока позволяет обнаружить переподключение.

`ready` подтверждает запуск и идентичность core; `linkValid` дополнительно требует действующего подтверждённого lease, heartbeat и открытого проверенного потока. `live` требует ещё согласованного снимка без ожидающих событий, поэтому его обновление может временно снять `live`, сохранив `linkValid`. Host оценивает эти признаки и сроки на один момент: ближайшая граница — минимум начала последнего heartbeat плюс интервал его свежести, срока lease и начала последнего успешного probe плюс интервал свежести probe; на границе срок истёк. Обычная команда повторно проверяет свежесть после предварительного чтения, но даже при `live` может быть запрещена журналом попыток или ядром. Stop сохраняет отдельный путь, а чтение состояния не продлевает право управления. Внутренние обязанности host — подтверждения связи, lifecycle потока, ledger, bounded-доставка и shutdown — разделены под прежней синхронизацией; карта владельцев и фактические проверки приведены в [host-session.md](host-session.md).

Desktop подписывается на ограниченные уведомления и перечитывает согласованное состояние; пассивное наблюдение не продлевает heartbeat. Для heartbeat Wails использует одноразовый допуск с четырёхсекундным сроком, отсчитываемым монотонно в host; после допуска получение или продление права имеет отдельный трёхсекундный предел. Один уже отправленный heartbeat может завершиться после закрытия UI в пределах этих интервалов. При неизвестном исходе команда не отправляется повторно автоматически; её идентификатор сохраняется для проверки. Оставшиеся проверки desktop и локального IAB перечислены в плане.

Frontend использует один наблюдатель для пары `hostRunId`/`backendRunId`. Подписка работающего интерфейса запускает heartbeat, при последней отписке прекращаются новые вызовы, периодические таймеры и подписки. Watchdog уже начатого вызова может оставаться до его завершения или своего срока и не запускает новую работу без слушателей. Замена wrapper отзывает подтверждение, но не освобождает слоты фактически незавершённых вызовов; их поздние результаты не подтверждают новый канал. Наблюдатель сохраняет границы ревизий, последовательностей и поколений, терминальный неизвестный исход первого получения управления и последний известный снимок. Проекция отдельно сообщает подтверждение связи, пригодный снимок, последний известный снимок и разрыв графика; последний снимок доступен отдельному пути Stop без признания его свежим. Учёт попыток, их хранение и дополнительные ограничения команд принадлежат frontend-координатору команд, а окончательное решение о допуске — в core. Жизненный цикл и фактические проверки описаны в [session-observation.md](session-observation.md).

История возвращает последнюю подтверждённую запись SQLite и не заменяет живой снимок активного испытания. Страницы списка ограничены 500 записями и упорядочены по UUID, не по времени; `nextAfter` задаёт курсор продолжения. Страницы не являются единым снимком: запись до курсора видна при новом обходе. Измерения и аудит также ограничены 500 элементами на страницу, номера аудита могут иметь пропуски. Все чтения требуют действующего права UI; отзыв до проверки после чтения отменяет ожидание и не допускает выдачу результата. Уже допущенный HTTP-ответ может доставляться после отзыва, но время отправки ограничено; для browser-session и WebSocket действуют отдельные требования отзыва.

`Event` с типом `stateChanged` требует обновить снимок; `measurement` и `commandChanged` несут соответствующие данные. Реализация валидирует обязательные поля, допустимые сочетания и входные данные: генерация Go/TypeScript не заменяет runtime-валидацию. Текущий контракт не описывает полный сценарий по ТЗ, управление приводом или политику реальных приборов.

Core использует `Engine.Changes()` как объединяемое уведомление и формирует последовательные события `stateChanged`; это не журнал каждого измерения или перехода. Снимок и его граница последовательности согласуются, переполнение ограниченной очереди закрывает подписку и WebSocket. Поток требует bearer и действующего права UI; отзыв, смена подписки или завершение core прерывают его. Проверка права допускает очередной кадр; кадр, допущенный до отзыва, может начать или завершить передачу позднее, уже отправленные байты отозвать нельзя. Разрешено не более двух одновременно открывающихся или завершающихся соединений; срок записи ограничен, а поток не продлевает право UI. Revision может не изменяться при новом измерении: клиент следует последовательности и обновляет снимок, не отбрасывая уведомление только из-за равной revision.

Нативный клиент подключается с закреплённым TLS и проверяет текстовые JSON-кадры по OpenAPI; размер одного кадра ограничен 65536 байтами, этот предел соблюдает и отправитель. После `StreamReady` клиент читает события в очередь до 64 кадров, получает снимок и передаёт только события после его границы по порядку. Пропуск, переполнение, неправильный кадр или разрыв завершают поток с ошибкой; владелец обязан получить новую подписку и снимок. Контекст `OpenStream` задаёт время жизни возвращённого потока. `Next` и обновление снимка использует один последовательный потребитель; закрытие потока не продлевает и не отзывает право UI. Полученный снимок сам по себе не подтверждает актуальность интерфейса, пока последующие уведомления не обработаны. Поскольку снимок не содержит статусы всех команд, после любого снимка, который мог покрыть ещё не полученный `commandChanged`, владелец перечитывает отслеживаемые незавершённые команды; при ошибке чтения их исход остаётся неизвестным. Нативный `Probe` проверяет ответ этого WebSocket в пределах двух секунд и завершает поток при ошибке; вызов ограничен одной проверкой. Ответ подтверждает связь только в момент проверки, но не доказывает живость UI, действующее право или актуальность снимка. Периодическая проверка и восстановление подключены в host; управляемый разрыв и восстановление наблюдались в окне с диагностическим core. Версии и ограничения опыта приведены в [журнале](first-core-demo-verification.md).

Контроллер движка ограничивает изменяющие команды периодом владения UI. Отзыв запрещает позднее подтверждение и сохраняет намерение системной остановки даже при ещё неразрешённом создании; исход создания уточняется чтением, без повтора команды. Core при потере владельца завершает движок с ограниченным ожиданием; подтверждённая запись и успешная остановка симулятора различаются. При неподтверждённом результате core удерживает хранилище и блокировку профиля до выхода процесса: операция, игнорирующая отмену, может оставаться в работе. Проверены потеря владельца с активным испытанием в отдельном процессе и зависшая запись через `core.Run` с настоящими HTTP-маршрутами.

Менеджер права хранит одного владельца. Отзыв и сигнал закрытия происходят в контроллере под общей блокировкой; срок проверяется при допуске команды и ожидающей записи. Новый владелец может получить доступ к неподтверждённому состоянию, но изменяющие команды во время незавершённой остановки получают ответ о занятости. Продление не отменяет уже ожидающую запись; транзакция, допущенная до истечения права, может завершиться позднее. Маршруты права, снимка, команд и регистрации WebSocket используют эту границу.

## Чтение для общего интерфейса

`ListTestsParams` поддерживает `q` (подстрока UUID или изделия, Unicode simple folding), `createdFrom` включительно, `createdBefore` исключительно и один существующий `outcome`. Фильтры соединяются AND и применяются ко всей подходящей истории в Store до формирования страницы. `%` и `_` являются обычными символами. Порядок остаётся UUID ASC: `after` — последний возвращённый UUID, `limit` — 1–500, по умолчанию 100. Между страницами возможны новые записи или изменение исхода; это не единый неизменный снимок.

Границы `createdAt` передаются как исходные строки RFC 3339 с точностью до наносекунды. Они проверяются до преобразования в `time.Time`, включая Wails-вызов: дополнительные дробные разряды не обрезаются, пустая недопустимая граница или исход не превращаются в отсутствие фильтра. Browser/core используют один разбор этого read-only запроса; измерения и аудит сохраняют прежние правила своих страниц. Store обходит ограниченные порции записей, закрывая курсор между ними; отмена возвращает ошибку, а не успешную неполную выборку. База и схема сохранённых записей не меняются.

`Snapshot.measurementTiming` — nullable оперативное наблюдение Engine: `elapsedSeconds` и `remainingSeconds` на последнем принятом в очередь отсчёте. Источник — та же монотонная разница, которую использует существующее измерение. До первого отсчёта и вне измерения поле равно `null`. Нулевой остаток не означает завершения: сохранение и завершение оборудования ещё могут продолжаться. Поле не записывается в исторический `TestRecord`; UI не завершает этап своим таймером и не обновляет пригодность снимка по ходу локальных часов.

## Проверка browser-ответов (#20)

Результат этапа: каждый используемый HTTP/WS-ответ browser-host проверяется до передачи UI. Проверяемые поверхности — реальные browser adapter/entry с подменой только транспорта, общий корпус исходных JSON в TypeScript и Go/schema, затем штатный demo-host. Не меняются исходная строка попытки, технологический допуск, identity/correlation, monotonicity, freshness, Storage/volatile, независимая Stop и no-autoretry. Scope — browser boundary, существующие схемы и контрактные проверки; core/SQLite/таймауты, рефакторинг координаторов, U01 и #21 не входят. Блокер для отдельного решения — необходимость менять публичное или предметное поведение вместо проверки существующих ответов.

Выбран один централизованный набор чистых guards `browser-responses.ts` без новой зависимости: он использует существующие generated-типы, не вводит свою модель DTO или JSON Schema interpreter. Общий корпус проверяется также существующим Go-компилятором OpenAPI Draft 2020-12 с `AssertFormat` и `UseNumber`. Корпус доказывает перечисленные случаи, не математическую эквивалентность всех возможных JSON. Production `ResponseValidator` и цепочка OpenAPI → Go → Wails сохраняются. Только уже существующие ticket/WS envelopes получают недостававшее описание; новых операций нет.

| Граница / endpoint | Схема или правило | Проверка / потребитель |
|---|---|---|
| core → Go host | Handshake, Snapshot, Readiness, TestRecord/List, Measurement/AuditPage, CommandStatus, Event | `ResponseValidator` до Go DTO; контекстные ID/порядок страниц отдельно в transport |
| GET status, POST verify | DesktopStatus → Handshake | browser guards; host/backend и revision — DesktopApp |
| POST session/check | BrowserSessionTicket | browser guards; ticket/deadline — session observation |
| POST session/heartbeat | HTTP 204, доступное тело пусто | после чтения тела и проверки канала; это не доказательство отсутствия скрытых wire-байтов при нарушении HTTP |
| GET session/view, observe | SessionView → ConnectionState, nullable Snapshot | browser guards; identity/revision/sequence/сроки/gap — session observation |
| GET session/wait | ConnectionNotice → nullable Event | browser guards; курсоры, ACK, поколения — session observation |
| GET tests/{id}/readiness | Readiness → ReadinessCheck | browser guards; test/revision и порядок — readiness observation |
| GET tests, tests/{id} | TestList / TestRecord → TestParameters | browser guards; generation/страницы — History |
| GET measurements, audit | MeasurementPage / AuditPage → Measurement / AuditEvent | browser guards; контекст страницы остаётся у прежнего потребителя |
| POST create/start/confirm/stop | CommandDispatch → CommandStatus | guards до normalizeCommandDispatch; exact identity/terminal — command coordinator |
| GET commands/{id} | CommandStatus | browser guard даже для предусмотренного, сейчас не вызываемого UI-пути |
| POST lookup-exact | ExactLookupResult → CommandStatus | guards и raw duplicate-key check; match/conflict принадлежат сверке, не прямому receipt |
| WS session/stream | BrowserControl / BrowserChannelId | entry guard; текущий socket/channel, bounded reconnect и abort остаются BrowserApp |
| Host → Wails | прежние сервисы/типы, Event/ConnectionState/DesktopStatus | штатная регистрация и generation; общие координаторы сохраняют проверки identity/freshness также для Wails |

Все успешные JSON HTTP-маршруты требуют 200; heartbeat — 204. HTTP-ошибка отвергается, её недоверенное тело не передаётся в UI и не распознаётся как command conflict. После полного чтения байтов тела повторно проверяется текущий канал. UTF-8 декодируется с fatal-ошибкой; ведущий BOM сохраняется для отказа JSON.parse, как в Go JSON decoder. Повреждённые байты не заменяются на U+FFFD перед проверкой. Сырые повторяющиеся ключи и некорректные Unicode-строки отвергаются до shape-validation; validators не вызывают сеть или retry. Прямой typed conflict остаётся `CommandConflictError`, exact conflict — результатом lookup; malformed ответ после отправки сохраняет unknown.

Ограничения JavaScript учитываются отдельно от OpenAPI: счётчики требуют safe integer; не представимые конечным Number значения и десятичные дроби, округлившиеся к целому/нулю, отвергаются на этапе разбора текста. Это не изменение схемы: `1.0`, `1e3` и обычное округление дробей вроде `0.1` допустимы. Корпус помечает более консервативную JS-политику отдельно. Schema-корпус сохраняет decimal через UseNumber; он не приравнивает схему к дополнительным float64-ограничениям production inputValue и последующему строгому декодированию числовой лексемы в Go integer. Parser-level случаи отдельно проверяют существующий строгий Go-разбор. `maxLength` считает Unicode code points, не UTF-16 units.

Нормативные основания: [OpenAPI 3.1.2](https://spec.openapis.org/oas/v3.1.2.html#schema-object), [JSON Schema validation 2020-12](https://json-schema.org/draft/2020-12/json-schema-validation), [ECMAScript JSON.parse](https://tc39.es/ecma262/multipage/structured-data.html#sec-json.parse), [Fetch](https://fetch.spec.whatwg.org/#fetch-method). TypeScript predicates не заменяют runtime-проверки; отказ guards используется с throw, а не как доказательство обратной ветки типа. `JSON.parse context.source` и обновление TS compiler/API для этого этапа не требуются.
