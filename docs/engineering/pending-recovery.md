# Восстановление наблюдений команд

Список принадлежит конкретной `databaseId`. При возврате компонента после отказа записи он согласует память с актуальным Storage; восстановление не отправляет команды повторно. Снятие блокировки новых обычных команд требует успешной записи согласованного списка. Stop отправляется отдельным путём с существующими ограничениями.

| Ситуация | Правило |
|---|---|
| Точное совпадение | `id`, вид, испытание, действие и исходная строка JSON совпадают; доступное подтверждение из памяти сохраняется за этой попыткой. |
| Одинаковый `id`, но другое содержимое | Записи остаются отдельными; результат одной не переносится на другую. |
| Разные базы | Память и Storage разделены по `databaseId`. |
| Прежняя запись без JSON | Сохраняется как непроверяемая; точная сверка без исходного содержимого не выполняется. |
| Ошибка чтения или записи | Неизвестность сохраняется, обычные команды блокируются; известные попытки остаются видимыми. |
| Более 65 записей после объединения | Записи не обрезаются; сохранение и обычные команды блокируются до уменьшения списка. Stop остаётся доступной в пределах существующих ограничений. |
| Прекращение наблюдения | Удаляется только выбранная точная запись; действие подтверждается успешной записью. При ошибке запись остаётся видимой. |

Для повторной активации Stop в локальной записи создаётся новая версия наблюдения. Она позволяет отличить обновление другой вкладки от старого снимка; версия не входит в идентичность команды и не отправляется ядру. Старые записи без версии остаются допустимыми.

Storage не сохраняет статус ответа команды. Подтверждение в памяти переживает перемонтирование компонента, но после полной перезагрузки страницы нужна повторная точная сверка.

## Граница переноса учёта попыток (#16)

Основание — принятый `main` `87f1f8aef268b6aabdbad1c011010b6ec39b50b4` после #12–#15. Перенос структурный: формат schema 2, исходный JSON, сроки и технологические правила не меняются. Результат — один frontend-владелец persistence, отправки и сверки вне React; формы, черновики и навигация остаются в React. Core по-прежнему владеет авторитетным результатом и аудитом.

| Состояние / переход | Сохранённое правило | Регрессия в `tests/live-flow.test.tsx` |
|---|---|---|
| Обычная попытка → отправка | Сначала успешное локальное сохранение; при отказе команда не отправляется | `persists` / сохранение до вызова service |
| Reserved Stop → отправка | ID задан ядром; отдельные слоты Stop и exact lookup; отказ Storage не запрещает отправку | `keeps Stop available and reserves its identifier when the command list is full` |
| Неизвестный результат → сверка | Exact lookup исходных байтов; remount/reconnect не повторяют команду | `does not replace a confirmed command with a late unknown exact lookup` |
| Подтверждённый результат | Terminal не понижается; direct receipt и exact lookup — разные свидетельства | `distinguishes a Stop lookup conflict from rejecting the actual request` |
| `receiptRequired` | После восстановления нужна сверка, даже если память сохранила terminal | `keeps an unpersisted Stop observable across remount when session storage fails` |
| `retired` | Прекращение наблюдения не означает успех; реактивация Stop получает новую версию | `retains a reactivated Stop after an unsuccessful removal` |
| Legacy | Без исходного JSON нельзя подтвердить исход по ID; ручная проверка не устанавливает результат | проверки `legacy` |
| Volatile → восстановление | Согласовать актуальный Storage и память, намеренные удаления и реактивацию, не обрезать overflow | `preserves a newer shared attempt when restoring an unpersisted Stop`; `retains overflow until multiple requested removals can be saved, while Stop remains available` |

Это независимые измерения: `completed` совместим с `receiptRequired`, неизвестный результат — с `retired`; версия наблюдения не является статусом команды. Отсутствующий JSON несовместим с точной сверкой; повреждённый список не считается пустым.

Сохранённая идентичность относится к `databaseId` и пяти полям точной попытки. Достоверность наблюдений дополнительно относится к host/backend и поколению consumer. Принятая проекция #15 остаётся единственным источником связи и пригодности снимка; координатор не запускает heartbeat и не рассчитывает lease. Замена service-wrapper той же сессии сохраняет принятую семантику уже начатого вызова; смена identity или dispose запрещает публикацию старого результата новому consumer. Физические слоты `call-limits` живут до settle Promise, независимо от отписки и watchdog.

Readiness выделяется в `readiness-observation.ts`: отдельный реестр по service/host/backend/test/revision с прежними лимитами и сроками. Отписка снимает listener и таймер новых чтений; уже начатое чтение освобождает место после settle. Readiness не владеет попытками команд и не зависит от их координатора.

Проверка переноса: unit-тесты модели и координатора без React/Wails, сохранённые React-регрессии #12–#15, целевые call-limits/live-form/session-view/session-observation, затем check:pr и desktop/browser-сборки. Реальные demo-проходы и диагностические подмены учитываются отдельно. Блокер для пользовательского решения — необходимость изменить принятое поведение или внешний контракт; обычные внутренние границы выбираются по коду.

### Владение и lifecycle после переноса

`command-attempt-state.ts` содержит формат записей, точную идентичность, монотонное согласование и восстановление памяти по базе. `command-coordinator.ts` — единственный владелец текущего списка, сохранения, отправки, exact lookup, исходов и сообщений. `LiveApp` больше не сериализует команды и не меняет журнал; он вызывает Create/Start/Confirm/Stop и отображает кэшируемую проекцию через `useSyncExternalStore`. Сигнал подтверждённого создания обрабатывает сохраняющийся родитель формы: временное снятие рабочего экрана не теряет очистку принятого черновика.

Создание координатора и чтение `getSnapshot` не читают Storage и не вызывают сервис. После React commit сначала передаётся принятая проекция #15 через `update`, затем `start` восстанавливает список и подписывается на page-wide слоты. До start действия не исполняются. `dispose` инвалидирует поколение consumer и снимает подписку на слоты; отписка React отдельно снимает listener отображения. Возврат рабочего экрана повторно вызывает start и согласует актуальное хранилище. Память базы и фактически незавершённые вызовы переживают этот цикл. Координатор сохраняется в родителе до смены host/backend/database/адаптера Storage; память восстановления живёт в пределах страницы по databaseId.

При смене wrapper новые действия используют новый `DemoService`, а уже начатый вызов сохраняет исходный сервис и конверт. Согласование запускается при изменении списка или входного наблюдения, по одному действию за проход. Изменение текста сообщения и освобождение физического слота только публикуют проекцию и не образуют бесконечный повтор lookup. Сами вызовы по-прежнему завершают page-wide слот в finally исходного Promise. У координатора нет собственного heartbeat, lease, сетевого watchdog или технологического автомата.
