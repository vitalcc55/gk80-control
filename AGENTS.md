# Repository Guidelines

## Назначение и источники

ГК80 — русскоязычное Windows-приложение для испытания клапанов на герметичность. Первая версия демонстрирует одну рабочую точку при Pmax производителя на симуляторе. Направление нагнетания/разрежения и наличие привода задаются отдельно.

Используйте предметное ТЗ и паспорта оборудования как основания требований; UX/UI-гайд — как общую политику интерфейса. Различайте установленное требование, предложение по интерфейсу и временное правило демонстрации. Сохраняйте оригиналы и пользовательские изменения; локальные документы не публикуйте автоматически и проверяйте их доступность в каждой рабочей копии.

В `docs/private-sources/` находятся локальные исходные документы; этот каталог игнорируется Git и не переносится в новую копию автоматически. Авторские политики хранятся в `docs/policies/`, пригодные для открытого репозитория инженерные конспекты — в `docs/engineering/`. Не переносите в открытые материалы подписи, персональные данные и идентификаторы конкретных приборов; уточняйте допустимость других сведений до публикации.

## Область первой версии

- Ручной клапан и клапан с приводом; нормальный проход, остановка, потеря ДД1, восстановление интерфейса и повторное открытие истории. Данные и режим явно обозначены как демонстрационные; core не допускает реальное оборудование в demo.
- Используйте явно обозначенного фиксированного оператора и записывайте идентификатор его действий. Полноценные роли, реальные драйверы, многоточечные серии, ручной пульт, калибровка, служба, установщик и автообновление не входят в первую версию.
- Официальный протокол, его печать и экспорт не входят в первую версию; форму ожидаем от заказчика. До согласования расчёта показывайте расход как «не рассчитан», класс — как «не определён». Непосредственно измеряемые demo-величины можно усреднять с указанием источника и интервала.
- Критерий окончания снижения давления, реакция оборудования на потерю связи, резервирование ДД2/ДД3, температурные каналы, расчёты, классификация и права на инженерные параметры требуют согласования. Не выдавайте временные demo-правила за требования реального стенда.

## Архитектура и контракт

- Desktop состоит из двух процессов: React → тонкий Go-адаптер Wails → локальные HTTP/JSON и WebSocket → отдельный Go core → порт оборудования, симулятор и SQLite. Core собирается независимо от Wails и React; симулятор реализует порт оборудования.
- Core владеет машиной состояний, проверкой команд, таймерами, качеством измерений, журналом и хранением. UI отвечает за отображение и несохранённый ввод; адаптер не содержит алгоритма испытания, расчётов или доступа к БД.
- Контракт интеграции задавайте в OpenAPI и схемах событий; типы получайте по цепочке OpenAPI → Go DTO → привязки Wails для TypeScript. Проверяйте генерацию и события; не поддерживайте вторую расходящуюся схему.
- Core слушает только `127.0.0.1`; авторизуйте HTTP и WebSocket случайным секретом между нативными процессами. Не передавайте секрет через URL, аргументы процесса, журналы или frontend. Предоставляйте предметные операции, а не универсальный HTTP-прокси.
- Повтор `commandId` не повторяет действие; тот же ID с иным содержимым отклоняется. При неизвестном исходе получайте состояние. Версия API, `backendRunId`, ревизия и последовательность событий позволяют восстановить полный снимок после пропуска или перезапуска без повторной отправки команд.
- Для одной конфигурации не допускайте двух ядер или активных испытаний. Отсутствующее или устаревшее измерение не равно нулю; принятие команды не равно выполнению. После аварии ядра запись остаётся неполной или прерванной, испытание автоматически не возобновляется.

## Интерфейс и браузерная работа

- Основной маршрут: Испытания → Параметры → Готовность → Проведение → Результат. Давление и перепад показывайте раздельно; команда приводу не подтверждает положение клапана. Отделяйте исход испытания, качество данных и результат сохранения.
- Используйте единые React-компоненты и предметную границу данных для desktop, просмотра подготовленных состояний и IAB с ядром. Для раннего прототипа допустимы локализованные временные типизированные модели; согласуйте их с общим контрактом при интеграции, не создавая вторую машину состояний.
- Предусмотрите `ui:fixtures` для связанных экранов и воспроизводимых состояний без Wails, core, SQLite и подключения к внешним сервисам. Постоянно обозначайте «Макет · подготовленные данные»; переходы показа не доказывают выполнение, измерение или сохранение. Готовность к показу не означает согласование заказчиком.
- Предусмотрите отдельный локальный режим `iab:demo` с теми же экранами, настоящим core, симулятором и demo SQLite. Способ браузерного входа выбирайте после проверки применимости и защиты; не создавайте второй транспорт или отдельный процесс без необходимости. Browser-host не входит в desktop-поставку.
- Браузерный вход допускает только demo core и предоставляет один локальный origin. Секрет core остаётся в Go. Проверяйте авторизацию сессии для прикладных HTTP и WebSocket, Host/Origin и защиту изменяющих запросов; при отзыве сессии прекращайте доступ, включая открытый WS. Открытые маршруты начала сессии и проверки доступности не выдают данные испытания. Не считайте loopback или проверку Origin достаточной авторизацией.
- На demo-профиль допускается один активный UI-клиент: IAB либо desktop; второй получает отказ. Refresh и HMR восстанавливают снимок и поток без повторных команд. Закрытие вкладки не доказывает остановку; после ограниченного времени восстановления core применяет документированную demo-процедуру. Завершайте только принадлежащие запуску процессы.
- IAB и desktop при последовательном открытии одного demo-профиля читают общую историю через core. Refresh и повторный запуск её не очищают; сброс — отдельное явное действие. Для визуальных замечаний используйте штатные аннотации IAB без собственного сервиса комментариев.

## Данные, аудит и диагностика

- SQLite принадлежит core и находится в пользовательском каталоге отдельно от установки. Сохраняйте demo-признак, версию схемы, параметры, оператора, исходные измерения с единицами, временем, качеством и источником, команды и события. Новое испытание по старым параметрам получает новый ID и новые подтверждения.
- Техническую диагностику ведите через общий `log/slog` в структурированных JSONL с отдельными файлами процессов и сквозными идентификаторами. Авторитетный аудит и измерения хранятся в SQLite core, а не подменяются диагностическим логом.
- Предметное состояние и соответствующее событие аудита записывайте атомарно. При невозможности обязательной записи блокируйте новые изменяющие действия; остановка остаётся доступной, а её результат зависит от подтверждения core. Ошибка технического лога сама по себе не подтверждает остановку или успешное сохранение.
- Ограничивайте очереди, объём записей и ротацию; обнаруживайте ошибки writer и потери. Логи не должны блокировать управление или содержать секреты, полные запросы и массивы измерений. Диагностика host работает и при недоступном core.

## Стек и проверки

Используйте Go, Wails, React/TypeScript, npm, Tailwind/shadcn, Zustand, uPlot, SQLite и Biome. Фиксируйте согласованные стабильные версии и lock-файлы; версии Wails CLI, Go-модуля и frontend runtime должны совпадать. Не обходите peer-конфликты. Команды и фактическую структуру определяйте по существующей конфигурации; имена будущих режимов не означают, что они уже реализованы.

Проверяйте изменения по затронутому поведению. Для раннего прототипа достаточно работающего маршрута и воспроизводимых состояний, проверки типов, lint, сборки и визуального просмотра; он не ждёт ядра или диагностики. Для настоящего обмена проверяйте отдельные процессы, авторизацию, события, повтор команд и запись. Итоговая приёмка включает ручной клапан, привод, остановку, потерю ДД1, восстановление связи, повторное открытие сохранённых и прерванных записей и защиту HTTP/WS.

Для frontend используйте `npm run check:quick` при правках и `npm run check:pr` перед передачей; предупреждения Biome считаются ошибками. Установка зависимостей выполняется отдельно. Состав проверок и ограничения текущего этапа описаны в `docs/engineering/quality-workflow.md`.

Для итоговой приёмки проверяйте совместную работу в IAB, включая аннотацию и повторный просмотр того же состояния, а также собранное desktop-приложение на целевой Windows с WebView2. Для раннего прототипа при недоступности IAB допустим обычный локальный браузер с указанием ограничения. Браузерный макет, сборка и тест с реальным ядром подтверждают разные свойства; фиксируйте результаты и ограничения каждого.
