# ГК80: правила разработки

ГК80 — русскоязычное Windows-приложение для испытания клапанов на герметичность. Текущий этап — одна рабочая точка на симуляторе. Поведение demo не подтверждает требования и безопасность реального стенда.

## Источники и область продукта

- Указывайте основание новой возможности: ТЗ, согласованное представление, правило demo или открытый вопрос оборудования. Согласование экрана не утверждает методику. Недостающее основание обозначайте явно.
- Конспекты — `docs/engineering`, политики интерфейса — `docs/policies`. Оригиналы в `docs/private-sources` игнорируются Git и могут отсутствовать в другой копии. Сохраняйте оригиналы и изменения пользователя; не публикуйте частные документы, подписи, персональные данные и идентификаторы приборов.
- Ближайший продукт: одна точка при Pmax, независимые параметры направления и привода, явно обозначенный фиксированный demo-оператор. Расширяйте сценарий завершёнными задачами с работающим GUI. Реальные драйверы, многоточечность, роли, ручной пульт, калибровка, служба, установщик и автообновление требуют отдельного объёма.
- До согласования расчётов и формы протокола расход — «не рассчитан», класс — «не определён»; официальные протокол, печать и экспорт не добавляются. Для среднего измеряемой demo-величины укажите источник и интервал.
- Таймауты, снижение давления и реакции симулятора на потерю связи/датчиков — документированная demo-политика, не требования будущего стенда. Не вводите технологические запреты без предметного основания. Вопросы — [open-questions](docs/engineering/open-questions.md).

## Владельцы и границы решений

| Область | Окончательное решение / ответственность |
|---|---|
| Право UI | Core выдаёт и проверяет lease; host/UI его не предоставляют |
| Испытание | Go Engine принимает решения; оборудование исполняет запрос и возвращает результат |
| Сохранённые данные и аудит | Store в единственном core; GUI и host не обращаются к SQLite |
| Процесс core | Owner завершает только принадлежащие запуску ресурсы |
| Соединение / пригодность проекции | Host координирует соединение; frontend-наблюдатель оценивает полученную проекцию |
| Попытки оператора | Frontend-координатор сохраняет точную попытку и сверяет её с core |
| Представление | React: формы, навигация, ограниченный контекст просмотра |
| Диагностика | Writer процесса; технический лог не заменяет аудит SQLite |

Окончательное решение имеет одного владельца. Проверки формата, свежести и допуска на разных границах обеспечивают разные гарантии; не создавайте второй независимый источник одного правила. Связь, пригодность снимка, право UI, допустимость команды и сохранение — разные факты.

## Проектирование изменения

- Для существенного изменения зафиксируйте в issue/PR результат, основание, владельца решения и исполнителя, состояния/ресурсы, затронутые границы, штатный проход/отказ/восстановление и приёмку. Локальной правке не нужен отдельный проектный документ.
- Переходите прямо к целевой модели и удаляйте заменённый путь, ненужные типы и флаги. Адаптер совместимости или двойная запись требуют названного потребителя либо сохраняемых данных, причины и условия удаления.
- Удаление прежней логики не разрешает терять историю, неизвестные попытки или профиль. При смене формата определите судьбу существующих данных; сброс допустим для согласованных одноразовых demo-данных. Миграции гипотетических версий не нужны.
- Представление меняется в UI. Новый этап требует решения Engine и данных контракта, не второго автомата React. Изменение wire-контракта обоснованно затрагивает схему, генерацию, проверки и потребителей.
- У ресурса определите владельца, ключ изоляции, завершение и предел удержания. Новые очереди, кэши и защитные слои требуют конкретного основания. Имена различают запрос, исполнение и сохранение; комментарии объясняют причины и инварианты. Уменьшение файла не заменяет разделение обязанностей.

## Проверка и завершение

Одна ветка/PR — один принимаемый результат. Не согласовывайте каждый локальный шаг; слияние и расширение объёма определяются поручением пользователя.

Проверки выбирайте по границе изменения и приёмке задачи. Регрессия выявляет исходную ошибку, структурная правка сохраняет зафиксированное поведение. Проверяйте штатный проход наряду с отказом. Для документации проверьте правила и ссылки, без повторной приёмки EXE.

Существенное изменение алгоритма, контракта или хранения проходит отдельное review по требованиям и diff, включая тесты. Заключение автора не заменяет эту проверку; несколько агентов одного аккаунта не означают несколько GitHub approvals.

Укажите SHA, проверки, среду и ограничения: fixtures, отдельный core, IAB и Windows/WebView2 доказывают разные свойства. Недоступная проверка остаётся непроверенной. Выполнение критериев завершает задачу; соседняя находка не расширяет её автоматически. Исторические выводы дополняйте новыми фактами.

## Code Review Rules

- Отмечайте конкурирующих владельцев, неявное продление доверия и технологические решения в UI/host.
- Проверяйте основание совместимости и новых ограничений, удаление заменённого пути и завершение ресурсов; штатный сценарий должен оставаться проходимым.
- Сопоставляйте вывод с доказательством: сборка и fixture не подтверждают оборудование, нативный GUI или сохранение в SQLite.
