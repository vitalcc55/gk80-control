# Контракт первого demo core

Статус: проектируется для первого упрощённого прохода. [OpenAPI](../../api/core.yaml) — единый источник HTTP-моделей и полезных нагрузок событий. Перечисленные операции не считаются реализованными только потому, что они описаны в схеме. Параметры, состояние, история и измерения принадлежат ядру; модели `src/model.ts` относятся к подготовленному макету.

## Процессы и доступ

Desktop запускает отдельный core с demo-профилем. Core удерживает блокировку профиля до выхода; два ядра и два активных UI-клиента для одного профиля не допускаются. Путь SQLite определяется профилем и располагается в пользовательском каталоге постоянных данных, отдельно от установки. Процессы тестов получают отдельные временные профили.

В дополнение к межпроцессному секрету core выдаёт одному UI-клиенту ограниченное по времени право управления (`ui-lease`): host получает, продлевает и освобождает его, а операции и поток привязаны к этому праву. Продление вызывается по активности самого React, а не живому host или подключённому WebSocket. При освобождении или истечении права core закрывает связанный WebSocket; отзыв браузерной сессии также прекращает её открытые соединения. Второй клиент получает отказ; восстановление прежнего клиента допускается только в пределах установленного срока и при отсутствии параллельного владельца. Browser-host отдельно связывает право core с авторизованной вкладкой и не считает общую cookie доказательством единственности вкладки. Точные сроки и механизм browser-session проверяются при её реализации.

Предлагаемый native bootstrap: host создаёт случайный секрет и передаёт его дочернему core по закрытому каналу стандартного ввода, не через аргументы или переменные окружения. Core после блокировки профиля открывает только `127.0.0.1` на свободном порту и сообщает адрес, версию, demo-признак и идентичность через канал стандартного вывода. Для проверки идентичности каждого соединения предполагается локальный TLS с временным сертификатом, отпечаток которого передаётся по этому каналу; клиент проверяет его до отправки bearer, не использует proxy и не следует перенаправлениям. HTTP и WebSocket используют одну проверку. На Windows отдельно проверяется защита bind от повторного захвата адреса. Это проект до реализации и процессных проверок, а не утверждение, что защита уже работает.

Host управляет только запущенным им процессом и ожидает его завершения. Закрытие канала владельца и исчезновение UI обрабатываются документированной demo-процедурой с ограниченным временем восстановления; ни исчезновение вкладки, ни запрос остановки не подтверждают безопасного давления. Выбор и проверка browser-host остаются отдельным этапом: assets middleware Wails 3 не защищает все маршруты его событий и WebSocket.

## Команды и сохранение

Все предметные изменяющие команды имеют `commandId`. Core сначала распознаёт повтор по ID и содержимому, затем проверяет ревизию и допустимость нового действия. Повтор не выполняет действие второй раз, тот же ID с иным содержимым отклоняется. `202` означает принятие, а не выполнение; повтор уже обработанной команды возвращает её известное состояние, включая ошибку выполнения. При неизвестном ответе host запрашивает состояние или команду, не отправляя её автоматически повторно. Подтверждения оператора относятся к новому испытанию и проверяются ядром при старте.

При создании испытания core заранее выделяет и вместе с записью сохраняет `stopCommandId`, предназначенный только для остановки этого испытания. Остановка имеет фиксированное содержимое и доступна при устаревшей ревизии или отказе записи; в работающем процессе её повтор не инициирует процедуру заново. Если записать результат невозможно, состояние сохранения остаётся ошибочным или неизвестным. После аварии испытание не возобновляется, а повтор зарезервированной остановки не возобновляет процедуру. Этот вариант требует проверок отказа SQLite, повторов, коллизий и аварийных окон до заявления о выполнении инвариантов.

Изменение сохраняемого состояния и соответствующий аудит записываются одной транзакцией. При отказе обязательной записи новые старты и обычные изменяющие действия не выполняются; остановка не зависит от успешной записи. Аудит не подменяется JSONL-диагностикой. Исход, качество данных и сохранение различаются; отсутствие значения не является нулём. До согласования расход не рассчитывается, класс не определяется.

## Поток и восстановление

Клиент подписывается на авторизованный WebSocket и после `StreamReady` буферизует события. Затем получает согласованный `Snapshot` с `backendRunId`, ревизией и `lastEventSequence`, отбрасывает события до границы снимка и применяет следующие по порядку. При смене запуска, пропуске, переполнении или разрыве поток восстанавливается новым снимком; до восстановления прежние показания не считаются актуальными. Host сообщает интерфейсу состояние соединения отдельным типизированным событием `core:connection` и предоставляет его начальное значение. UI подписывается до чтения начального состояния и применяет только более новую ревизию данного `hostRunId`; смена host означает новое восстановление. `live` разрешён лишь после согласованного снимка и потока. Очереди ограничены, потеря событий не скрывается. Времена наблюдений абсолютные, время последнего достоверного измерения указывается отдельно; таймеры принадлежат ядру. Чтение исходных отсчётов и аудита ограничено страницами: последовательности начинаются с 1, курсор 0 или его отсутствие означает начало. Пустые обязательные коллекции кодируются массивом `[]`, а не `null`.

`Event` с типом `stateChanged` требует обновить снимок; `measurement` и `commandChanged` несут соответствующие данные. Реализация валидирует обязательные поля, допустимые сочетания и входные данные: генерация Go/TypeScript не заменяет runtime-валидацию. Текущий контракт не описывает полный сценарий по ТЗ, управление приводом или политику реальных приборов.
