# Сборка, генерация и проверки

Эти правила применяются к `scripts`, npm-профилям и конфигурации инструментов. Команды и закреплённые версии берите из `package.json`, lock-файлов и [development-environment](../docs/engineering/development-environment.md). Не дублируйте номера версий и количество тестов в политиках.

## Воспроизводимое выполнение

- Setup и проверка — разные действия. Проверка не должна молча устанавливать инструменты, менять lock-файл или скачивать другой toolchain. Используйте существующий npm/Go/Wails workflow; не обходите peer-конфликт принудительной установкой. CLI, Go-модуль и frontend runtime Wails обновляются согласованно.
- Профиль исполняет настоящие проверки production-кода и возвращает их ненулевой код/ошибку запуска. Неподдерживаемая среда или отсутствующая зависимость не превращается в успешный skip. Не создавайте заглушку Service или урезанный набор под названием полного профиля.
- Не ослабляйте критерии, пороги, эталоны или область проверки ради успешного отчёта. Адресное исключение имеет причину и область; изменение ожидаемого поведения подтверждается требованием и review.
- Изолируйте временные файлы, demo-профили и порты. Завершайте только процессы, созданные текущим запуском. Не удаляйте историю пользователя и private-sources; сборка и отчёты остаются в предусмотренных игнорируемых каталогах.
- Учитывайте рабочий каталог, пути с пробелами и наследуемые переменные. Профиль не должен незаметно пропускать тесты из-за внешних фильтров/workspace. Не меняйте глобальную конфигурацию окружения ради локального запуска.
- Generated-файлы обновляются штатной генерацией. Проверяющий режим сравнивает результат без изменения исходников; режим записи включается явно. Правила схемы — [api/AGENTS.md](../api/AGENTS.md).

## Выбор контура

| Затронутая область | Применимая проверка |
|---|---|
| Frontend | `check:quick` при разработке, `check:pr` перед передачей frontend-изменения; реальные live-сценарии по задаче |
| Общий host | `check:host`; при изменении конкурентности — применимый `--race`; изменения runner — `check:host:runner` |
| Wails/генерация | Windows `check:host:native`, `contract:check`/`contract:test` по изменённой границе |
| Go core/Engine/Store | Тесты затронутых пакетов и их интеграции, применимые vet/lint/race по [quality-workflow](../docs/engineering/quality-workflow.md) |
| Окно и демонстрационный проход | Сборка desktop и наблюдение Windows/WebView2; IAB и аннотации проверяются отдельно |
| Только документы/политики | Ссылки, актуальность команд, непротиворечивость и применение правил к типичным задачам |

Существующие профили описаны в [quality-workflow](../docs/engineering/quality-workflow.md) и [host-checks](../docs/engineering/host-checks.md). Наличие имени будущего профиля в issue не означает, что команда уже существует. Расширяйте набор под установленный риск и требования задачи; GitHub Actions не является обязательной инфраструктурой проекта.

При изменении runner проверяйте не только успешный запуск, но и передачу настоящего отказа. Повтор полного контура нужен после относящегося к нему изменения, нового отказа или по критерию приёмки; документальная правка не требует нового оконного прохода. Отчёт связывает фактическую команду, среду и SHA и различает исполненную проверку, опубликованное прежнее доказательство и непроверенную границу.

## Code Review Rules

- Отмечайте успешный статус при пропуске, скрытой установке или отказе дочернего процесса; безопасный путь — явная диагностика и ненулевой код.
- Отмечайте подмену production-кода ради переносимости, незаявленный фильтр тестов и изменение пользовательских данных при cleanup.
- Проверяйте, что новый профиль даёт самостоятельную гарантию, а его название и отчёт не обещают больше выполненного.
