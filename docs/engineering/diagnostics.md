# Диагностика процессов

В `internal/diagnostics` подготовлена общая основа `slog`/JSONL для desktop и core. Оба процесса создают отдельные файлы, а host записывает идентификатор подтверждённого core. Core записывает принятие и результат команд первого прохода и безопасные причины отказа; сквозная диагностика от экрана ещё не подключена. Аудит испытаний и измерения принадлежат SQLite, не этому журналу.

Каждый запуск получает собственный файл `<role>-<process_run_id>.jsonl` в каталоге логов demo-профиля вне установки и исходников, например `%LOCALAPPDATA%\GK80\demo-gk80-control\logs`. Примерный каталог и профиль для рабочего ПК описаны в [окружении](development-environment.md); параллельные копии используют разные профили. Идентификатор запуска core совпадает с `backendRunId`, при необходимости host также записывает этот идентификатор для корреляции.

В записи есть версия схемы, время UTC, уровень, фиксированное сообщение, код события, компонент, роль и идентификатор запуска процесса, PID, версия сборки, профиль и режим; при наличии добавляются существующие `command_id`, `test_id`, `action_id`, `backend_run_id`, разрешённый код причины и код выхода. Прикладные компоненты используют `Application` и обычный `*slog.Logger`: сообщением служит код события из каталога, а `With` передаёт только разрешённые идентификаторы и значения. Идентификаторы принимаются как UUID или его строка; группы не поддерживаются. Неизвестные сообщения и сгруппированные записи отбрасываются с учётом потерь, произвольные атрибуты не записываются. Каталог включает события принятия, отклонения и выполнения команды; `command.observed` с ограниченным `command_status` отдельно отмечает повторное чтение результата, не утверждая повторного выполнения. Адаптеры Wails и библиотек заменяют сообщения и атрибуты фиксированными `framework.message` и `library.message` с соответствующими компонентами, framework DEBUG отключён. Секреты, payload и произвольные ошибки не передаются в журнал.

Время JSONL — время регистрации записи логгером, а не метка транзакции: при задержанном ответе хранения и асинхронной обработке наблюдение результата может появиться раньше записи о его принятии. Авторитетный порядок сохранённых действий и изменений задаёт аудит SQLite. События движка поступают через ограниченную неблокирующую очередь; её потери передаются в диагностику с количеством и уровнем, включая ERROR, и не задерживают остановку.

Очередь ограничена, отправка записи не ждёт файлового I/O. Один worker владеет файлом; текущий файл ограничен 16 МиБ, а короткая запись, ошибка writer, переполнение очереди и достижение лимита переводят статус в degraded и учитывают потерянные записи по уровням. Частичная запись может оставить неполный последний фрагмент JSONL; предыдущие полные строки остаются читаемыми, а дефект отражается в статусе. Fallback пробует один фиксированный текст через отдельный worker, не через тот же logger и не через stdout core; его успех при зависшем или неисправном выводе не гарантирован. Закрытие ожидает освобождения writer и попытки fallback не более двух секунд или до более раннего переданного deadline. После аварийного завершения сохранность очереди не обещается.

Если завершение writer не подтверждено в отведённое время, состояние диагностики становится degraded без утверждения о количестве потерянных записей. Core дополнительно сообщает об этом ограниченным кодом завершения: host замечает его даже при недоступном stderr. Пока окно работает, предупреждение о журнале показывается в нём; отказ, обнаруженный только после закрытия окна, в React не доставляется. Fallback журналирования остаётся ограниченной попыткой и не гарантирует запись. Состояние журнала не означает успеха или ошибки сохранения испытания.

Политика аварийного уведомления описана в [правилах интерфейса](../../src/AGENTS.md#всплывающие-элементы-и-окна). Фатальный маршрут пока не соответствует ей полностью: Wails 3.1.0 синхронно вызывает обработчик и затем завершает процесс, а текущий host показывает `MessageBox` без подтверждения недоступности WebView. Передача управления приложению потребует проверки обоих мест выхода в Wails и их вызывающих путей: простое удаление `os.Exit` может продолжить выполнение после фатальной ошибки. Ожидание ответа React в обработчике может заблокировать поток окна; отсутствие ответа по тайм-ауту само по себе не доказывает отказ WebView. Исправление зависимости и нативная проверка целевого маршрута ещё не выполнены.

Полная ротация, очистка и общий бюджет закрытых файлов разных запусков относятся к уровню Б #8; текущий модуль не ограничивает их суммарное накопление. Его файловая диагностика не останавливает испытание и не подтверждает сохранение аудита. Окно показывает сигнал деградации диагностики процессов; подробная диагностика React остаётся последующим этапом.

Локальные целевые проверки: после подключения окружения выполнить `go test ./internal/diagnostics` и `golangci-lint run ./internal/diagnostics/...`. Тесты используют временные каталоги и управляемые ошибки/блокировки writer. `go test -race -count=1 ./internal/diagnostics` выполнен в Ubuntu/WSL с Go 1.27.3 и GCC 13.3; это проверка конкурентного модуля в Linux, не проверка Windows-процессов или файловых особенностей. Windows race-профиль с C-компилятором ещё не подготовлен.

## Безопасные категории Wails

Результат #21 (A09 из #11, узкая часть #8): известная категория или контролируемая точка отказа различима в JSONL, неизвестная причина не выдумывается. Проверяемые поверхности — настоящий пакет `internal/diagnostics` в закреплённой Linux-среде, включая race, Windows mapper с настоящим типом Wails, native bindings/сборка и отдельно контролируемые отказы в настоящем Wails. Scope ограничен каталогом/сериализацией, Windows hooks и этими тестами. Ротация, новая телеметрия, старые framework-причины, core/SQLite, команды и IAB shutdown не входят. Необходимость менять публичное поведение или порядок shutdown требует отдельного решения; маскировать её под диагностику нельзя.

| Источник | Достоверный факт | `error_code` / `operation` | Доступные ID |
|---|---|---|---|
| `Options.ErrorHandler`, `errors.As` распознал `*application.FatalError` | Типизированная фатальность; точка приёма ошибки | `fatal_error` / `error_handler` | Только существующие process_run_id и PID desktop |
| Прочая ошибка `Options.ErrorHandler` | Известен callback, категория неизвестна | `unclassified` / `error_handler` | Тот же процессный контекст |
| `app.Run()` вернул error | Известна граница вернувшего ошибку вызова | `application_run_failed` / `application_run` | Тот же процессный контекст |
| Общий Wails `slog` ERROR и более высокий уровень | Достоверны только источник и уровень | `unclassified`, операция отсутствует | Тот же процессный контекст |

`operation` здесь — точка наблюдения, а не установленная операция-первопричина. Нельзя из `application_run_failed` заключать, что отказал WebView2. Callback не передаёт корреляцию конкретного backend/test/command: чтение текущего Owner не доказывало бы принадлежность ошибки этому состоянию, поэтому эти ID не добавляются. Обычные INFO/WARN общего framework logger и Library не объявляются ошибками.

Путь записи: тонкая Windows-часть определяет тип/место → `FrameworkFailure` принимает закрытые типизированные code/operation → неизменяемая копия `frameworkHandler` → существующие `emit`, очередь и единственный JSONL writer. Допустимые пары приведены выше; неверный код или несовместимая пара становятся `unclassified` без операции. Общий `fields.add` не получает новых разрешений. Входные сообщения, `Record.Attrs`, `.With`, группы, error/LogValuer, payload и секреты по-прежнему не читаются и не сериализуются; подставные ID не заменяют процессный контекст. Это специально ограниченная граница для недоверенных framework-данных, не обычная семантика `slog.With`.

Повторное получение такого logger не регистрирует callback и не создаёт worker. Бюджеты очереди/файла, счётчики потерь, fallback и ограниченное закрытие остаются прежними. Новый код не меняет predicate фатальности: mapper использует тот же `errors.As`, а его отдельный bool управляет прежней веткой cleanup независимо от фильтра logger. Заменяется одна запись callback; ветка Run пишет один контекст перед прежним фиксированным возвратом ошибки. Внутренние сообщения Wails могут независимо дать `unclassified`: это другой источник, без выдуманной связи между записями.

В Wails 3.1.0 `handleFatalError` синхронно вызывает ErrorHandler, затем `os.Exit(1)`. Поэтому прежняя последовательность внутри fatal callback сохранена: запись категории → owner.Close → process.stopped(exit=1) → bounded logger.Close → предупреждение при degraded → showFatal. Defer не заменяет эту очистку. Run-error использует прежние defer owner.Close и logger.Close. Не обещается две записи для одной fatal: нормальный fatal-путь выходит, а закрытый logger поздние записи не сохраняет.

Отдельная существующая граница: Chromium может вызвать callback с обычным error и затем `os.Exit(1)`. Нынешняя explicit cleanup выполняется только для типизированного fatal; для такого общего callback сохранность очереди и завершение core не доказываются. Это не исправляется в #21, а контролируемая приёмка не использует сломанный путь WebView2 для провоцирования этого случая.

Основания решения: [Go 1.27.3 Handler](https://pkg.go.dev/log/slog@go1.27.3#Handler), [JSONHandler](https://pkg.go.dev/log/slog@go1.27.3#JSONHandler.Handle) и [LogValuer](https://pkg.go.dev/log/slog@go1.27.3#LogValuer); закреплённые [Wails FatalError](https://github.com/wailsapp/wails/blob/v3.1.0/v3/pkg/application/errors.go), [ErrorHandler/Run](https://github.com/wailsapp/wails/blob/v3.1.0/v3/pkg/application/application.go); [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). Рекомендации сверены с закреплёнными исходниками; произвольные значения не становятся безопасными только из-за применения JSONHandler или LogValuer.

Добавленная characterization-регрессия до реализации падала: обычный framework ERROR не содержал явного `unclassified`. После реализации конечный JSONL настоящего logger через `memoryWriter` проверяет семь пар code/operation на четырёх разрешённых уровнях, процессный контекст, отсутствие вымышленных business ID, секретов, вложенных errors/LogValuer, `.With` и групп. Повторное/конкурентное получение handler даёт ровно одну запись на вызов и не изменяет исходный handler. Writer fixtures проверяют неблокирующий возврат logger, потери, единичный безопасный fallback и bounded close. Синтетический `subject result` этих тестов не является исполнением реальной команды. Diff подтверждает отсутствие изменений командного кода, а host-регрессии — его штатное поведение; фактическую команду при отказавшем writer в этом этапе отдельно не запускали. Прежний `TestEventsHaveSharedIDsAndFrameworkNeverWritesRawData` и проверки очереди/закрытия не ослаблены.

Нативное подключение проверено отдельно в двух диагностических копиях исходников `970fb26`, на отдельных demo-профилях, с настоящими production hooks, Wails 3.0.0 и core. Frontend assets взяты из штатной сборки; Go-код logger и hooks не подменялся. Сборки использовали обычные имена EXE и проектные теги. Единственные fault-изменения остались в игнорируемых копиях, не в поставляемом приложении:

1. **Typed fatal через настоящий WebView2 156.0.4314.58.** URL окна заменён на `/%ZZ?marker=wails-fatal-secret-marker`. `GetStartURL` вернул обычную ошибку разбора escape; код навигации Wails передал её в `handleFatalError`, который обернул её в `*FatalError` и синхронно вызвал зарегистрированный `Options.ErrorHandler`. Эта цепочка подтверждается закреплёнными исходниками и инъекцией; JSONL сам фиксирует категорию, а не весь внутренний путь. В нём ровно одна запись `fatal_error / error_handler`, PID 30252, без секрет-маркера, raw error и business ID. Подтверждены core PID 30488, `core.stopped` с exit 0, `process.stopped` desktop с exit 1 и фактический exit desktop 1 после закрытия штатного диалога. Это искусственная ошибка конфигурации URL, не естественный сбой WebView2 и не объяснение старых framework.message.
2. **Возврат ошибки настоящего `app.Run()`.** Только в другой копии добавлен временный Wails service, чей `ServiceStartup` возвращает `wails-run-secret-marker`. Настоящий Wails startup вернул error до открытия рабочего окна; неизменённая production-ветка записала ровно одну `application_run_failed / application_run`, PID 10640. Маркер и payload в JSONL отсутствуют. Есть `process.stopped` core PID 32320 и desktop, фактический desktop exit 1. Записи `core.stopped` с числовым exit code здесь нет: выход core с кодом 0 этим сценарием не заявляется.

Оба системных диалога закрыты через Computer Use; сеанс освобождён. После завершения отдельно проверено отсутствие desktop/core и наблюдённого WebView2 этих запусков, принудительное завершение не применялось. Это не нормальный проход испытания и не повторная полная матрица IAB/Windows. Обычный неизвестный Chromium callback с немедленным exit не инъецировался; его описанное ограничение не объявляется исправленным.
